# 06 - Questions and Next Steps

## Open questions

Ordered by how much the answer changes the design.

1. **Who allocates `refund_no`, the store or the ERP?** §2, §6 and BR-07 say the store allocates it at record creation and uses it as the Create idempotency key. §9.5 says the ERP allocates it and returns it with the Create response. Both cannot hold: an ERP-allocated number cannot be the key for the very first Create, which is the call that can time out after the ERP accepted it. *Needed: which rule wins, and whether the ERP's own number must appear on the receipt.*
2. **Is the refund window 14 days from delivery (BR-02) or 7 days from receipt (contract note)?** The contract note also says CS must not be able to override it. *Needed: the contractual answer, and whether "delivery" and "receipt" are the same recorded date.*
3. **Can a refund be cancelled once the ERP has opened the credit note?** BR-09 says no. The lifecycle and ACL include `cancelled`, and `main` allows it from `cash_refund_pending`, with no ERP void call. *Needed: whether the ERP has a void operation.*
4. **What does a Create 409 mean operationally?** The ERP holds a credit note for that `refund_no` with a different payload. `main` marks the refund `failed`, which releases its quantity. *Needed: the ERP team's resolution process, so 409s can go to a held reconciliation state instead.*
5. **Is the Read Refund Status step operator-driven (§4) or a scheduled sweep (§9.2)?** *My design does both through one outbox path (`02`).*
6. **What does a 404 from Read Refund Status mean after the eventual-consistency bound?** On the running stack, the seeded `SR-ORD-1006` gets 404 on every check.
7. **Which record says a refund is "settled": `erp_confirmed` (§9.3) or the Settlement Adjustment Export acknowledgement (§9.4)?**
8. **How is shipping split between the seller and first-party items on a mixed order?** The order stores one shipping amount. I allocate the seller share in proportion to ex-tax line amounts (issue 13); if the business records the split at order placement, the calculator should read that instead.
9. **How do seller code, tax class, seller order ID and delivery date reach an order?** Nothing in the module or in Magento sets `mp_seller_code`, `mp_tax_class`, `mp_seller_order_id` or `mp_delivered_at`; only the assignment's seeder does. A storefront order therefore never offers a seller refund. I assume an upstream marketplace and delivery integration fills them (the FRD puts the order and fulfilment flow out of scope); I would confirm which system owns each field.
10. **Must native Magento credit memos count towards the refundable quantity?** The module counts only its own refunds. An order that also received a native credit memo could be refunded twice. Either seller orders never get native credit memos, or `PriorRefundQuantity` must include them.
11. **Which tax rate does a refund use: the rate the order charged, or the product's tax class?** FRD §11 says "the original order's tax rate". I use the order item's stored rate (issue 16) and send the tax class's business code to the ERP. Tax should confirm, especially for orders where the two differ.
12. **Which overview is authoritative?** The architecture overview describes a synchronous, controller-orchestrated design; the code on `main` is outbox-based. `03` reviews the document and notes the code at each point.
